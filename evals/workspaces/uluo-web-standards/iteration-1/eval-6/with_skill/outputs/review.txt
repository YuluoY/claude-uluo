问题 #1: DDD 层依赖违反 — Domain import 了 Infrastructure
---------------------------------------------------------------------------
严重程度: MUST (阻断)

文件 domain/order/order.entity.ts 属于领域层（domain），但它 import 了
../infrastructure/order.repository.impl。这违反了 DDD 分层架构的核心规则：

  Domain MUST NOT import from infrastructure layer.

根据 check-layer-boundary.js 自定义检查的正则模式:
  if (normalized.includes('/domain/') && importsLayer(content, 'infrastructure'))
    → addError: 'Domain MUST NOT import from infrastructure layer'

修复方向:
  在 domain 层定义一个 IOrderRepository 接口（抽象），entity 只依赖该接口。
  具体实现 OrderRepositoryImpl 保留在 infrastructure/，由入口文件（如
  setup.ts 或 main.ts）在依赖组装阶段注入，entity 通过构造函数参数接收
  已注入的仓储实例。

  示例:
  // domain/order/interfaces/order.repository.interface.ts
  export interface IOrderRepository {
    findById(id: string): Promise<Order | undefined>
    save(order: Order): Promise<void>
  }

  // domain/order/order.entity.ts
  import type { IOrderRepository } from './interfaces/order.repository.interface'
  export class Order {
    constructor(private readonly repo: IOrderRepository) {}
    // 不再 new OrderRepositoryImpl()
  }

问题 #2: 实体方法内直接 new 数据库仓储实例
---------------------------------------------------------------------------
严重程度: MUST (阻断)

在 Entity 的方法体中直接构造具体仓储实例 (new OrderRepositoryImpl())，
违反了三项依赖管理规则：

  - G3.1 显式注入: 依赖应通过构造函数参数或函数参数显式传入，而非在方法
    内部隐式创建。
  - G3.2 依赖接口: 业务代码应依赖抽象接口，不应直接依赖具体实现。直接
    new 导致 Entity 与 Infrastructure 强耦合。
  - G3.3 入口组装: 依赖图应在程序入口处组装，业务代码只消费已注入的依赖。

另外违反了 Tell, Don't Ask 与 Command-Query Separation——Entity 的职责是
封装领域规则，不应自己获取数据库连接。

修复方向:
  将仓储实例通过构造函数注入，在 Entity 方法中只调用 repo.xxx()，不创建。

问题 #3: 空 catch (e) {} 块 — 隐蔽的异常吞没
---------------------------------------------------------------------------
严重程度: MUST (阻断)

存在 catch (e) {} 块，异常被完全吞没，不做任何日志记录、转换或重抛。

违反的 soft-rules:
  - G2.1 禁止空吞异常: 每个 catch 块必须至少做日志记录或转换重抛。
  - G2.2 分层转换: 异常应在 domain → application → interface 逐层转换，
    不应让空 catch 阻断整个异常链。

违反的编码范式:
  - Fail Fast: 不应消音异常让坏数据继续向下游流动。
  - await-to-js: 异步错误处理应使用 [error, data] 元组解包模式，而非
    try-catch 嵌套。

修复方向:
  至少记录日志并重抛转换后的领域异常：
  方案 A (如果适用 await-to-js 模式):
    const [err, result] = await to(this.repo.findById(id))
    if (err) throw new OrderRetrievalError('Failed to retrieve order', err)

  方案 B (保留 try-catch 场景):
    try { ... }
    catch (e) {
      log.error('Order retrieval failed', { orderId: id, error: e })
      throw new OrderRetrievalError('Failed to retrieve order', { cause: e })
    }

问题 #4: any 类型标注
---------------------------------------------------------------------------
严重程度: MUST (阻断)

使用了 any 类型标注，违反 TypeScript 代码规范的零容忍原则。

typescript.md 明确规定:
  - any — 零容忍。eslint @typescript-eslint/no-explicit-any 已阻断。
  - 应用泛型、unknown 或具体类型替代 any。

修复方向:
  根据实际使用场景选择替代方案:
  - 函数参数 / 返回值: 使用具体 interface 或泛型约束 T
  - 接收不确定结构: 先用 unknown + type guard 收窄
  - 第三方库返回值: 查阅库的类型定义，使用正确类型

  示例:
  // ❌
  function parse(data: any): any {}

  // ✅ 泛型约束
  function parse<T>(data: string): T {
    return JSON.parse(data) as T
  }

  // ✅ unknown + type guard
  function handle(input: unknown) {
    if (typeof input === 'object' && input !== null && 'id' in input) { ... }
  }
