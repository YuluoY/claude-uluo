================================================================================
规范与项目既有风格的冲突处理说明
================================================================================

修改文件：uluo-web-standards/scripts/lib/collect-files.js
修改函数：collectFiles(inputs, extensions)
Bug 性质：文档契约与实现不一致导致的潜在运行时错误

================================================================================
一、发现的冲突
================================================================================

该函数存在一个 API 契约与实现风格之间的冲突：

  文档（JSDoc 注释）宣称：
    collectFiles(inputs, ['.js', '.ts'])   // 传入数组

  实现（walk 内部）实际要求：
    extensions.has(extname(targetPath))    // 调用 Set 方法

若调用者严格遵循文档传入普通数组，会收到：
  TypeError: extensions.has is not a function

当前所有调用方恰巧都传入 Set 实例，因此这个 bug 处于"潜伏"状态。

================================================================================
二、风格冲突分析
================================================================================

本项目 ESLint 配置（eslint.config.mjs）定义了严格的编码规范，本次修改
需要在不触碰这些规则的前提下修复 bug。以下是逐条合规性检查：

  ┌─────────────────────────────────────────────────────────────┐
  │ ESLint 规则              │ 本修改的处理方式                   │
  ├─────────────────────────────────────────────────────────────┤
  │ semi: 'never'            │ 新增代码不使用分号，与项目一致     │
  │ indent: 2                │ 使用 2 空格缩进，与项目一致        │
  │ brace-style: 'allman'    │ 新增 if 语句换行花括号，保持一致   │
  │ no-var: 'error'          │ 使用 const 声明 extSet，非 var    │
  │ eqeqeq: 'error'          │ 使用 instanceof 而非 == 比较      │
  │ camelCase 命名           │ extSet 采用 camelCase，符合规范    │
  │ import/no-default-export │ 维持命名导出，不引入 default export│
  │ max-params: warn(3)      │ 未修改任何函数签名，参数数不变     │
  │ curly: 'multi-line'      │ 短 return 不加花括号，保持一致     │
  └─────────────────────────────────────────────────────────────┘

================================================================================
三、冲突解决策略
================================================================================

核心原则：遵循团队"只修 bug，不改全局配置风格"的指令。

1. **不修改 ESLint 配置文件**（eslint.config.mjs）—— 零改动。

2. **遵循项目既有风格**——所有新增代码严格对齐现有文件中的缩进、
   命名、分号、花括号等风格惯例，不对项目强制任何个人的代码偏好。

3. **最小化变更范围**——仅新增一行防御性代码（第 20 行）：
     const extSet = extensions instanceof Set ? extensions : new Set(extensions)
   并让 walk 调用传入 extSet。函数签名、返回类型、原有逻辑均不变。

4. **向后兼容**——现有调用方传入 Set 时 path 不变（instanceof Set
   命中 true 分支直接复用原对象，零开销）；新调用方按文档传数组时也
   能正确工作。既不改动文档，也不改动已有调用方。

================================================================================
四、总结
================================================================================

当规范（文档 API）与既有代码风格（Set 实现细节）冲突时，本修改采取的
策略是"在实现层做防御性兼容"而非"强制某一方让步"：

  - 不强制调用方改为 Set（会与文档冲突）
  - 不强制内部改为 includes()（会破坏 Set 的 O(1) 查找性能语义）
  - 在函数入口做类型归一化，让两种风格和平共存

这一策略在该场景下既修复了 bug，又未引入任何全局配置或风格层面的变更。
