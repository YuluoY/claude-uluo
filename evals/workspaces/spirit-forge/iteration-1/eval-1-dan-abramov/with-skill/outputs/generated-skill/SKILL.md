# dan-abramov-gaearon-react-javascript

## Core Principles

1. When designing APIs; prefer start from the desired user experience and work backward; because starting from the API itself leads to changing the whole approach later to enable the right UX
2. When deciding where complexity should live; prefer put it in framework internals so product code stays simple; because something has to act as the coordinator; centralized complexity enables simpler application code
3. When users need capabilities the API doesn't yet support; prefer provide escape hatches and observe usage patterns; because battle-tested hacks reveal the right API design; entrenching a poor idiom is worse than temporary fragility
4. When designing component APIs; prefer enable developers to understand code by reading it locally; because in large codebases, developers only have local knowledge; editing code shouldn't require understanding the entire system
5. When tempted to remove duplication via abstraction; prefer tolerate repetition and verify the abstraction improves evolutionary flexibility; because abstractions impose costs; if requirements diverge from the abstraction's assumptions, it becomes an obstacle
6. When fixing a bug; prefer always establish a reliable reproduction first; because you cannot fix what you cannot reliably observe; without a repro, both humans and AI guess without verification
7. When narrowing down a bug; prefer remove things without testing theories (well-founded reduction); because building isolated cases to test hypotheses risks creating cases that don't exhibit the same bug
8. When thinking about side effects in React; prefer use the mental model of synchronizing external systems with props/state; because treating useEffect as lifecycle methods (mount/update) leads to stale closures and incorrect cleanup timing

## Gotchas & Anti-Patterns

_These are patterns that Dan Abramov (gaearon) consistently catches that others miss._

### 1. Lying about useEffect dependencies: using [] to 'run once on mount' but the effect reads props/state that change
**Fix**: Include ALL deps honestly, or change the effect to need fewer deps (functional updater, useReducer, hoist functions)

### 2. Treating useEffect as lifecycle (mount vs update distinction)
**Fix**: Think in terms of synchronization, not lifecycle. Props A->B->C should produce same result as rendering with C immediately.

### 3. Premature abstraction — removing duplication before understanding how requirements evolve
**Fix**: Let duplication live until you have evidence the abstraction improves evolutionary flexibility. 'Let clean code guide you. Then let it go.'

### 4. Race conditions in async effects: newer request completes before older one, stale state overwrites fresh state
**Fix**: Use a cleanup function with didCancel flag, or use Suspense for data fetching.

### 5. Theory-driven debugging: building isolated cases to test a hypothesis without first having a reliable repro
**Fix**: Establish repro first (what to do, expected, actual). Then narrow via theory-free reduction: remove things, test, commit only deletions that preserve the bug.

### 6. Designing APIs starting from the abstraction rather than the user experience
**Fix**: Start with desired UX and work backward. What interface feels natural to the end user?

### 7. Writing component code that requires knowledge of parent's DOM structure (findDOMNode anti-pattern)
**Fix**: Use declarative APIs. Props down, not imperative calls up. Enable local reasoning.

### 8. Wrapping everything in React.memo before measuring performance
**Fix**: Profile first. memo has its own overhead. Most components get new props that fail shallow comparison. Fix upstream object creation in render.

### 9. Storing derived/computed values in state instead of computing during render
**Fix**: Compute during render. If expensive, useMemo. Avoids sync bugs where derived state lags behind source.

### 10. Assuming state/props inside effects always reflect latest value (thinking like this.state in classes)
**Fix**: Every function captures its render's values. For imperative access to latest, use a ref as escape hatch.

### 11. Ignoring cleanup timing: assuming cleanup runs BEFORE next render
**Fix**: React runs previous cleanup AFTER next render AND browser paint. Write cleanup to be self-contained; its job is undoing the previous effect only.

### 12. Creating separate 'simple' vs 'advanced' API paths that require migration
**Fix**: Use progressive complexity — same structural approach scales from simple to complex without rewrites.

### 13. Accessibility as afterthought rather than default
**Fix**: Build accessibility into the framework and component library. Tooling and education should make the right path the easy path.
