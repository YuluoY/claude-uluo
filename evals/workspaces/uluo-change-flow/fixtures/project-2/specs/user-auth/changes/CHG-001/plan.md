# 认证模块 Session → JWT 变更 Plan

> 日期: 2026-06-25 | 作者: huyongle | 关联变更 spec: ./spec.md

## 技术方案选择

### 方案对比
| 方案 | 优点 | 缺点 | 复杂度 |
|------|------|------|--------|
| 方案 A: 纯 JWT（无状态） | 实现简单，完全无状态，扩展性好 | 无法主动失效 token，登出仅客户端清除 | 低 |
| 方案 B: JWT 加黑名单 | 可主动失效 token | 需引入 Redis 存储黑名单，增加状态依赖 | 中 |

### 选择结论
- **选择**: 方案 A
- **理由**: 当前阶段优先解决扩展性和跨域问题，主动失效可通过短期有效期加刷新机制缓解，避免引入 Redis 增加架构复杂度。

## Delta 规格

### MODIFIED: spec.md > ## 背景与动机
- **原文摘要**: "系统需要用户登录功能来保护敏感数据，目前使用 session 认证。"
- **改为**: "系统需要用户登录功能来保护敏感数据，使用 JWT 无状态认证机制，支持水平扩展和跨域访问。"

### MODIFIED: spec.md > ## 功能需求 > FR-1
- **原文摘要**: "触发条件: 用户提交登录表单；预期行为: 创建 session，重定向到个人中心；边界条件: 密码错误 5 次锁定账号"
- **改为**: "触发条件: 用户提交登录表单；预期行为: 验证凭据后签发 JWT token 并返回给客户端，客户端存储后通过 Authorization Header 携带；边界条件: 密码错误 5 次锁定账号，token 有效期 2 小时"

### MODIFIED: spec.md > ## 功能需求 > FR-2
- **原文摘要**: "触发条件: 管理员查看在线用户；预期行为: 显示当前活跃 session 列表；边界条件: 可强制下线指定用户"
- **改为**: "触发条件: token 即将过期时客户端请求刷新；预期行为: 验证当前 token 有效后签发新 token；边界条件: 旧 token 过期后不可刷新，需重新登录。原 session 列表和强制下线功能在无状态架构下不再支持。"

### MODIFIED: spec.md > ## 验收标准
- **原文摘要**: "FR-1: 登录成功后重定向到 /dashboard；FR-2: 管理员可查看和终止用户会话"
- **改为**: "FR-1: 登录成功后返回 JWT token，后续请求携带 token 可访问受保护接口；FR-2: token 过期前可请求刷新，刷新成功返回新 token，过期后返回 401"

### MODIFIED: spec.md > ## 调研依据 > 技术可行性
- **原文摘要**: "express-session | 可行 | Context7 | 高"
- **改为**: "jsonwebtoken | 可行 | Context7 | 高 — sign/verify API 满足签发和验证需求"
