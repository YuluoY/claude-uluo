# plan.md 模板（L2 变更 Plan）

L2 变更 Plan 聚焦方案设计——回答"怎么改"。使用 delta 格式描述对已有文档的修改，是 L1 spec 和 L3 tasks 之间的桥梁。

---

## 模板

```markdown
# [变更标题] 变更 Plan

> 日期: YYYY-MM-DD | 作者: [运行 git config user.name 获取] | 关联变更 spec: ./spec.md

## 技术方案选择

### 方案对比
| 方案 | 优点 | 缺点 | 复杂度 |
|------|------|------|--------|
| 方案 A | [优点] | [缺点] | [低/中/高] |
| 方案 B | [优点] | [缺点] | [低/中/高] |

### 选择结论
- **选择**: [方案 A / 方案 B]
- **理由**: [1-2 句话说明选择理由]

## Delta 规格

### MODIFIED: spec.md > ## 功能需求 > FR-1
- **原文摘要**: [摘录原文关键内容]
- **改为**: [描述修改后的内容]

### ADDED: spec.md > ## 功能需求 > FR-3
- **插入位置**: [在 FR-2 之后]
- **新内容**:
  ```
  ### FR-3: [功能名]
  - **优先级**: P0
  - **触发条件**: [条件]
  - **预期行为**: [行为]
  - **边界条件**: [边界]
  ```

### REMOVED: spec.md > ## 非目标
- **删除位置**: [## 非目标 下的第 2 条]
- **删除原因**: [为什么删除]

### MODIFIED: plan.md > ## 模块设计 > ### Service
- **原文摘要**: [摘录原文关键内容]
- **改为**: [描述修改后的内容]
```

---

## 填写指南

### 技术方案选择
- **不是必须的**——如果只有一个方案，可跳过整个"技术方案选择"小节
- 只有当存在多个可行方案、需要权衡时才填写
- 方案对比要客观——不要为了选某个方案而弱化它的缺点
- 复杂度评估的是实现难度，不是工作量
- 选择结论必须有理由，不能只写"选方案 A"

### Delta 规格
- 必须使用 `MODIFIED` / `ADDED` / `REMOVED` 三种标记之一
- 每个 delta 必须引用原文位置，格式：`文件名 > 章节 > 子章节`
  - 例如：`spec.md > ## 功能需求 > FR-1`
  - 例如：`plan.md > ## 模块设计 > ### Service`
- `MODIFIED` 项必须包含：
  - **原文摘要**：摘录原文关键内容，便于读者定位
  - **改为**：描述修改后的内容
- `ADDED` 项必须包含：
  - **插入位置**：明确在哪个章节之后/之前插入
  - **新内容**：完整的新内容（用代码块包裹）
- `REMOVED` 项必须包含：
  - **删除位置**：精确到章节内的具体条目
  - **删除原因**：为什么删除，便于追溯

### Delta 引用范围
- delta 不仅针对 spec.md，也针对 plan.md、tasks.md 等所有已有文档
- 如果变更涉及修改已有的 plan.md（如调整模块设计），也要写 delta

### 不要包含的内容
- 具体文件路径（那是 L3 tasks 的事）
- 行号（文档会变化，行号不可靠）
- 任务执行顺序（那是 L3 tasks 的事）
- 验收检查点（那是 checklist 的事）

### 大小控制
- L2 plan 的详细程度取决于变更复杂度
- 简单变更：3-5 个 delta 即可
- 复杂变更：可分模块组织 delta，但每个 delta 不超过 20 行
