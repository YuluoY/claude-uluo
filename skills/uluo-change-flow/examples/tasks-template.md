# tasks.md 模板（L3 变更 Tasks）

L3 变更 Tasks 聚焦执行任务——回答"具体改哪些文件"。定位到文件级，允许标注需要调研的任务。是变更落地的执行清单。

---

## 模板

```markdown
# [变更标题] 变更 Tasks

> 日期: YYYY-MM-DD | 作者: [运行 git config user.name 获取] | 关联变更 plan: ./plan.md

## 执行任务清单

### T1: [动词] [目标]
- **目标文件**: `src/[module]/[file].js`
- **任务类型**: 代码 / 文档 / 设计稿 / 测试
- **任务描述**: [动词开头：修改/新增/删除/重构] [具体做什么]
- **需调研**: [否 / 是 — 建议调研方式: WebSearch / MCP Context7 / GitHub / 官网文档]
- **依赖**: [无 / T1]
- **状态**: [ ] 未执行 / [x] 已完成

### T2: [动词] [目标]
- **目标文件**: `specs/[feature]/spec.md`
- **任务类型**: 文档
- **任务描述**: 修改 spec.md 的 FR-1 章节，更新触发条件
- **需调研**: 否
- **依赖**: 无
- **状态**: [ ] 未执行 / [x] 已完成

## 任务依赖图
T1 → T2 → T3
     T4（并行）
```

---

## 填写指南

### 执行任务清单
- 每个任务必须有唯一编号（T1、T2、T3...）
- 任务标题格式：`T1: [动词] [目标]`——动词开头，目标明确
- 每个任务必须包含以下字段：
  - **目标文件**：相对项目根的文件路径（如 `src/modules/coupon/service.js`）
  - **任务类型**：只能是 `代码` / `文档` / `设计稿` / `测试` 四种之一
  - **任务描述**：必须动词开头——`修改` / `新增` / `删除` / `重构`
  - **需调研**：`否` 或 `是`（标注时建议调研方式）
  - **依赖**：`无` 或依赖的任务编号（如 `T1`）
  - **状态**：`[ ]` 未执行 / `[x]` 已完成
- **执行回写纪律**：Phase 7 执行时，每完成一项任务立即把该项 **状态** 从 `[ ]` 改为 `[x]`——任务清单即进度看板，未勾选即未完成

### 目标文件
- 必须是相对项目根的路径，用反引号包裹
- 一个任务对应一个目标文件——如果需要改多个文件，拆成多个任务
- 如果是新增文件，路径就是将要创建的文件路径

### 任务描述
- 必须动词开头：`修改` / `新增` / `删除` / `重构`
- 描述要具体——"修改 FR-1 的触发条件" 比 "修改 spec" 好
- 不要在这里写代码片段——那是执行时的事

### 需调研标注
- 如果任务需要先调研技术方案（如不确定 API 用法、不确定框架能力），标注 `是`
- 标注 `是` 时必须建议调研方式：
  - `WebSearch`：搜索通用技术问题
  - `MCP Context7`：查询框架/库的官方文档
  - `GitHub`：参考开源项目实现
  - `官网文档`：查阅官方文档
- **调研不是强制步骤**——如果开发者已了解方案，可直接跳过
- 调研结论应记录在任务执行过程中，便于后续追溯

### 任务依赖图
- 用箭头 `→` 表示串行依赖
- 标注 `（并行）` 表示可并行执行的任务
- 依赖关系必须无循环——如果有循环，说明任务拆分有问题

### 不要包含的内容
- 验收检查点（那是 checklist 的事）
- "怎么验证改对了"（那是 checklist 的事）
- 代码片段（那是执行时的事）
- 技术方案对比（那是 L2 plan 的事）

### 大小控制
- 任务粒度适中——一个任务可在 30 分钟到 2 小时内完成
- 如果任务太大，拆分成多个小任务
- 如果任务太小（如改一行注释），合并到相关任务中
