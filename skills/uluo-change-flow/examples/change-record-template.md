# change-record.md 模板（留痕归档）

变更记录文档——变更归档时填写，记录变更的全过程信息。是变更工作流的最终产物，用于后续追溯和审计。

---

## 模板

```markdown
# [变更标题] 变更记录

> 变更编号: CHG-XXX | 变更日期: YYYY-MM-DD | 变更发起人: [运行 git config user.name 获取] | 状态: [已合并/已拒绝/进行中]

## 变更概述
[1-2 句话概述本次变更]

## 变更原因
[说明为什么需要变更]

## 影响清单
[引用 spec.md 的影响范围清单，或简要列出]

## 执行结果
- **执行任务数**: [N]
- **完成数**: [N]
- **失败数**: [N]
- **修改文件数**: [N]

## 验收结论
- **Review 结论**: [通过 / 不通过]
- **Review 日期**: YYYY-MM-DD
- **回退次数**: [N]
- **回退历史**:
  - 第 1 次回退: [层级] — [原因] — 已修复

## Diff 引用
- spec.md diff: [git diff hash 或简要说明]
- plan.md diff: [git diff hash 或简要说明]
- tasks.md diff: [git diff hash 或简要说明]
- 代码变更: [git commit hash 或简要说明]
```

---

## 填写指南

### 头部信息
- **变更编号**：必须与 `changes/CHG-XXX/` 目录名一致
- **变更日期**：变更归档日期（不是发起日期）
- **变更发起人**：[运行 git config user.name 获取]
- **状态**：只能是以下三种之一：
  - `已合并`：变更已合并到主分支
  - `已拒绝`：变更被拒绝，未执行
  - `进行中`：变更正在执行中

### 变更概述
- 1-2 句话概述本次变更
- 不要重复 spec.md 的全部内容——只写最核心的变更内容

### 变更原因
- 说明为什么需要变更
- 可引用 spec.md 的"变更触发原因"，但不要直接复制——用更简洁的语言概括

### 影响清单
- 可引用 spec.md 的影响范围清单（如 `详见 spec.md > ## 影响范围`）
- 也可简要列出关键影响项
- 不必重复全文——避免冗余

### 执行结果
- **执行任务数**：tasks.md 中的任务总数
- **完成数**：已完成的任务数
- **失败数**：执行失败的任务数
- **修改文件数**：实际修改的文件数量（包括文档、代码、设计稿）

### 验收结论
- **Review 结论**：必须与 checklist.md 的 Review 结论一致
- **Review 日期**：checklist 最终通过/不通过的日期
- **回退次数**：整个变更过程中回退的总次数
- **回退历史**：如有回退，必须记录每次回退的：
  - 回退层级（spec/plan/tasks/执行）
  - 回退原因
  - 修复状态

### Diff 引用
- 记录每个文档和代码的变更引用，便于后续追溯
- **spec.md diff**：spec.md 的 git diff hash 或简要说明
- **plan.md diff**：plan.md 的 git diff hash 或简要说明
- **tasks.md diff**：tasks.md 的 git diff hash 或简要说明
- **代码变更**：代码的 git commit hash 或简要说明
- 如果使用 git，可填写 commit hash；如果不使用 git，可填写简要变更说明

### 归档时机
- 变更状态为"已合并"或"已拒绝"时，才填写此文档
- 状态为"进行中"时，此文档可先创建，但验收结论和 Diff 引用待变更完成后补充

### 不要包含的内容
- 不要重复 spec/plan/tasks/checklist 的全部内容
- 不要包含代码片段
- 不要包含技术方案细节
- 这是归档文档，只记录"变更了什么"和"结果如何"，不记录"怎么做的"
