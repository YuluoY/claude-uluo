# spec.md 模板（L1 变更 Spec）

L1 变更 Spec 聚焦范围确定和决策——回答"为什么变更"和"影响什么"，不涉及具体实施细节。是变更工作流的入口文档，决定变更是否推进。

---

## 模板

```markdown
# [变更标题] 变更 Spec

> 日期: YYYY-MM-DD | 作者: `git config user.name` | 变更编号: CHG-XXX | 关联特性: specs/<feature-name>/

## 变更背景

### 变更触发原因
[1-2 句话说明为什么需要变更。例如：产品要求优惠券支持叠加使用，当前实现仅支持单张使用。]

### 变更目标
[1-2 句话说明变更要达成什么。例如：允许用户在同一订单中使用多张优惠券，按优先级叠加计算折扣。]

## 影响范围

### 文档影响
| 文档 | 章节 | 影响类型 | 风险等级 | 说明 |
|------|------|---------|---------|------|
| spec.md | ## 功能需求 > FR-1 | MODIFIED | 中 | [说明] |
| spec.md | ## 功能需求 > FR-3 | ADDED | 低 | [说明] |

### 代码影响
| 模块 | 影响类型 | 风险等级 | 说明 |
|------|---------|---------|------|
| [模块名] | MODIFIED | 高 | [说明] |

### 设计稿影响
| 组件 | 影响类型 | 风险等级 | 说明 |
|------|---------|---------|------|
| [组件名] | MODIFIED | 中 | [说明] |

> 注意：此处只精确到模块/目录级，不精确到文件路径。文件级定位在 L3 tasks 中。

## 决策结论

- **决策**: [批准 / 拒绝 / 需更多信息]
- **理由**: [1-2 句话说明决策理由]
- **缺失信息**（如决策为"需更多信息"）:
  - [信息项 1]
  - [信息项 2]
```

---

## 填写指南

### 变更背景
- 最关键的章节，决定变更是否值得推进
- 变更触发原因和变更目标都要简洁，1-2 句话即可
- 触发原因回答"为什么现在要变"，变更目标回答"变成什么样"
- 不要在这里写技术方案——那是 L2 plan 的事

### 影响范围
- 必须覆盖文档、代码、设计稿三个维度（如果有的话）
- 没有影响的维度可省略对应小节，但不要假装"没影响"
- 影响类型只能是：`ADDED` / `MODIFIED` / `REMOVED`
- 风险等级只能是：`高` / `中` / `低`
- 此处只精确到模块/目录级，**不精确到文件路径**——文件级定位是 L3 tasks 的事
- 风险等级评估的是"变更后可能出问题的概率和影响"，不是"工作量大小"

### 决策结论
- 必须有明确的决策：批准 / 拒绝 / 需更多信息
- 必须有理由——"批准"也要说明为什么批准
- 决策为"需更多信息"时，必须列出缺失的信息项
- 决策为"拒绝"时，理由要充分，便于后续追溯

### 不要包含的内容
- 具体文件路径（那是 L3 tasks 的事）
- 代码片段、行号
- 技术方案选择（那是 L2 plan 的事）
- 任务执行顺序（那是 L3 tasks 的事）
- 验收检查点（那是 checklist 的事）

### 大小控制
- L1 spec 应该简洁——控制在 50-80 行以内
- 如果写得太长，说明你在写 L2 plan 的内容，应该拆分
