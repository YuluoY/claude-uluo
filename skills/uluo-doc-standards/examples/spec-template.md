## 填写指南

### 背景与动机
最关键的章节。如果读者只能读一段，就读这段。回答"不改会怎样"。

### 用户故事
背景解释了"什么问题"，用户故事说明"谁的问题"——这是被跳过后会让需求走偏的章节。

- 用标准格式：**作为 <角色>，我希望 <功能>，以便 <价值>**
- 角色要具体——"运营人员"、"系统管理员"、"普通用户"、"合规审计员"，不要泛泛写"用户"
- 验收线索列告诉读者：这个故事的完成情况由哪条 FR 或验收标准来衡量
- 如果某个故事对应的 FR 还没出现（如运维的故事对应的是"非功能性需求-可维护性"），标注清楚
- 容易被忽略的角色：运维（监控/告警）、合规（审计日志）、客服（查询后台）、其他系统（API 调用方）

### 非目标
和"目标"同等重要。避免范围蔓延。把"容易误以为要做但实际不做"的事写清楚。

### 功能需求
- 每个 FR 编号唯一，可被其他文档引用
- "边界条件"不要跳过——正常流程谁都写得好，异常处理才是水平
- 优先级用 P0/P1/P2：P0 本次必做，P1 本次做不完了就下期，P2 知道了就行

### 非功能性需求
- 不要只写"高性能"——写出数字：QPS 多少？P99 延迟多少？
- 如果没有特殊要求，标注"N/A"

### 调研依据
最容易被跳过但其实最关键的章节——它就是 spec 的可信度证明。
- 每个技术可行性判断都应该有信息源——Context7 验证 API 能力、GitHub 验证方案成熟度
- 性能目标不能拍脑袋——必须有业界基准做参照（WebSearch 搜索）
- "可信度"不是装饰：来自官方文档的是"高"，来自个人博客只说了一句话的是"低"
- 如果某个调研项没有信息源、纯凭经验估计——标注清楚

### 参考资料
- 按信息源类型分组列出，方便读者按需检索
- Context7 / GitHub / WebSearch / SO 四类必须覆盖，缺的标注"N/A"
- 链接尽量可点击——Markdown 格式就是最好的格式

### 验收标准
- 必须是可验证的——"用户体验好"不是验收标准
- 每条验收标准对应一个或多个 FR
- 写成 checklist 格式，写完代码后逐条对照

### 大小控制
- 小功能：spec.md 控制在 200 行以内
- 大功能：可以更详细，但每个需求描述不超过 10 行
