plan 总入口——回答全局性的"怎么做"和"为什么这样选"。如果涉及多个大 slice（后端/前端/数据迁移等），README.md 只写全局决策和架构概览，细节拆分到子 plan 文件。

```
plans/
├── README.md              ← 总入口（必存在）：全局架构 + 跨 slice 决策
├── backend-architecture.md← 后端方案（多 slice 时拆分）

└── data-model.md          ← 数据模型专篇（涉及多表时拆分）
```

## 填写指南

### 架构概览
- 用文字 + Mermaid 流程图描述整体方案，Markdown 原生支持 Mermaid 渲染
- 画出关键模块、数据流方向和外部依赖，不画实现细节
- 如有复杂组件间交互，使用 Mermaid 的 flowchart/sequence 补充

### 关键设计决策
最核心的章节。每个决策必须包含"选择了什么"+"为什么选"+"还考虑过什么"。只记录有争议或非显而易见的决策，不要把"用 MySQL"这种项目已有的默认选项也写进去。

### 代码库分析
这是 plan 质量的根基。不读源码写的 plan 是纸上谈兵。

- **现有架构约束**：观察当前项目的每一层怎么写代码——Controller 用什么注解？Service 是接口+实现还是直接类？Repository 用什么 ORM？
- **锚点模块分析**：选一个和新功能最像的已有模块，通读它的代码。所有观察结果填入表格，新代码照此风格写
- **可复用清单**：先查一遍已有的类和方法，能复用的不要重写。这是 tasks 中"复用"标注的来源
- **需要变更的已有模块**：最小的侵入是最好的侵入——如果改了老模块，说清为什么和风险

### 模块设计
- 一个模块一个模块写，每个说清职责、接口、依赖
- 如果模块和已有代码结构一致，标注"沿用现有模式"
- 接口签名使用代码块标注语言

### 数据模型
- 新增表写完整 DDL，变更表写明变更类型
- 字段说明不用太啰嗦——字段名本身就应该足够清晰

### API 契约
- 请求/响应用 JSON 示例
- 错误码不要漏——调用方最关心异常情况

### 测试策略
- 至少列出单元测试和集成测试
- 标注使用的测试框架

### 回滚方案
- 没有回滚方案的计划是不完整的
- 最简单的回滚就是 feature flag——推荐
