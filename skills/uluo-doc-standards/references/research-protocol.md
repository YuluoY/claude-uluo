# 信息调研协议

spec 是源头，其质量决定了后续所有文档和代码的质量。spec 不能凭空写——它必须是需求目标驱动的、多轮迭代的、多渠道交叉验证的深度调研结论。

> 本文件是 [spec-template.md](../examples/spec-template.md) 的前置协议。产出 spec 之前必读。

---

## 核心原则：以需求目标为导向

调研不是"每个信息源查一次"的打卡动作。调研的目的是回答 spec 必须回答的问题。同一个信息源可能被反复查询多次——每次针对需求的不同侧面：

- 分析需求目标，列出必须回答的**知识缺口清单**
- 对每个缺口，选择最合适的信息源组合进行定向搜寻
- 同一信息源可以被反复查询——每次针对不同的问题
- 当某个关键结论影响需求走向时，必须引入第二/第三源交叉验证
- 收集到的信息整合后，如果发现新的缺口，启动新一轮调研
- 停止条件：所有 spec 关键要素（可行性、方案、基准、风险）都有可信来源支撑

## 调研路径

```
需求目标
    │
    ▼
┌─────────────────────────────────────┐
│  知识缺口清单                        │
│  - 谁会用到？涉及哪些角色？          │
│  - 目标技术栈能不能做？查什么？       │
│  - 有什么成熟方案可以参考？查什么？    │
│  - 业界性能/安全基准是什么？查什么？   │
│  - 已知的坑有什么？查什么？           │
│  - 项目现有架构怎么适配？查什么？      │
└─────────────────────────────────────┘
    │
    ▼
对每个缺口：选源 → 搜索 → 整合 → 发现新缺口？→ 再搜
    │
    ▼
所有缺口闭合 → spec 可以定稿
```

## 信息源矩阵

每个信息源擅长回答不同类型的问题。调研中根据具体问题动态选择，而非按固定顺序遍历：

| 信息源 | 权威 | 擅长回答的问题 | 典型用法 |
|--------|------|---------------|---------|
| **Context7 MCP** | ⭐⭐⭐ | "这个框架能不能做 X？""这个 API 的能力边界在哪？""官方推荐的做法是什么？" | 反复查询：一个需求可能涉及多个框架特性的验证 |
| **GitHub** | ⭐⭐⭐ | "别人怎么实现类似功能的？""这个方案有什么已知 bug？""生产环境踩过什么坑？" | 反复查询：参考架构设计、ER 模型、API 设计、测试策略 |
| **WebSearch** | ⭐⭐ | "业界同类功能的性能基准是什么？""主流方案对比？""最新的技术趋势？" | 反复查询：竞品分析、技术选型论证、性能预期设定 |
| **Stack Overflow** | ⭐⭐ | "这个具体问题怎么解决？""这个错误的根因是什么？""社区共识方案是什么？" | 反复查询：每个技术难点的社区方案 |
| **项目源码分析** | ⭐⭐⭐ | "项目现有的技术栈是什么？""已有模块怎么写代码的？""哪些可以直接复用？" | 持续分析：整个调研过程中不断对照项目现状 |

## 调研深度判断

不是所有问题都需要所有源。根据问题对 spec 的核心程度决定调研深度：

| 问题类型 | 最少调研深度 | 示例 |
|---------|------------|------|
| spec 核心走向 | L3（三源交叉） | "用什么方案做库存扣减？"——搜 GitHub 方案 + WebSearch 对比 + Context7 验证可行性 |
| 关键决策支撑 | L2（双源比对） | "性能目标定多少？"——WebSearch 找业界基准 + GitHub 看同类项目实测 |
| 辅助信息确认 | L1（单源定向） | "OrderService 的接口签名是什么？"——直接读项目源码 |
| 已知坑点排查 | L2（双源比对） | "MyBatis Cursor 有什么坑？"——SO 找报错 + GitHub issues 看仍未修复的 bug |

## spec 定稿前复盘

spec 不是调研完了才写——调研和 spec 撰写是交替迭代的。定稿前必须复盘：

- [ ] spec 中每个关键断言（"X 方案可行"、"性能目标应 ≤ Yms"）能否追溯到具体信息源？
- [ ] 用户故事是否覆盖了所有受影响角色？有没有遗漏运维/合规/客服/外部调用方？
- [ ] 核心方案是否经过了多源交叉验证（至少 L2）？
- [ ] 调研过程中有没有因为发现新信息而修正过 spec 的某个结论？
- [ ] 如果某个结论只有单一来源，是否在 spec 中标注了可信度？
- [ ] 参考资料是否按信息源类型分组列出，方便读者溯源？
