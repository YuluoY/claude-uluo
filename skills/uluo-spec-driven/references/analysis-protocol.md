# 源码分析协议

plan 和 tasks 不是从模板里填出来的——它们是对当前项目代码库进行深度分析后得出的执行路线图。如果 spec 定义了"目的地"，那源码分析就是绘制"从这里到目的地"的精确地图。

> 本文件是 [plan-template.md](../examples/plan-template.md) 的前置协议。产出 plan 之前必读。

---

## 分析流程

写 plan 和 tasks 之前，必须对项目源码进行以下层次的分析：

| 分析层次 | 产出 | 对应文档 |
|---------|------|---------|
| **架构层** | 当前分层结构、模块边界、通信方式、已有设计模式的惯用法 | plan 的"架构概览"和"关键设计决策" |
| **模块层** | 每个相关模块的职责、接口签名、依赖链、现有类似模块的实现风格 | plan 的"模块/组件设计" |
| **数据层** | 现有表结构、Entity 定义风格、ORM 使用方式、迁移工具和规范 | plan 的"数据模型"、tasks 的 Phase 1 |
| **代码层** | 命名规范、错误处理模式、日志/监控埋点方式、测试框架和风格 | tasks 每个任务的具体实现要求 |

---

## 分析方法

1. **定位锚点模块**：找到和新功能最相关的已有模块，通读其代码——它就是新代码的样板
2. **追踪调用链**：沿用户请求路径（controller → service → repository → entity），理解每一层的职责边界和惯用写法
3. **识别可复用接口**：查找已有的 service/repository/util，判断哪些可以直接复用、哪些需要扩展
4. **分析相似场景**：如果项目里有过类似功能的实现（如已有"满减活动"模块要新增"优惠券"），直接对照差异

## 源码分析在 plan 中的体现

plan 的每一项设计决策都应该能追溯到具体的源码依据：

```markdown
# ❌ 不合格
### 决策 1: 使用策略模式
- **选择**: 策略模式
- **原因**: 策略模式适合多种算法

# ✅ 合格——有源码依据
### 决策 1: 使用策略模式
- **选择**: 策略模式
- **原因**: 项目已有 PaymentStrategy 的实现模式（见 src/.../payment/strategy/），
  且 pom.xml 中没有引入规则引擎依赖。复用现有模式减少认知负担
- **替代方案**: 规则引擎——需要新增依赖，与项目现有风格不一致
```

## 源码分析在 tasks 中的体现

tasks 的每个任务都应该明确标注"产出物放在哪个包"、"遵循什么已有规范"、"依赖哪个已有模块"——而不是泛泛地写"创建 Service 类"：

```markdown
# ❌ 不合格
- [ ] **T2.1**: 实现优惠券校验逻辑
  - **产出物**: CouponValidator.java

# ✅ 合格——有源码依据
- [ ] **T2.1**: 实现优惠券校验逻辑
  - **产出物**: `coupon/domain/CouponValidator.java`（新增）
  - **参考**: 参考 `order/domain/OrderValidator.java` 的实现风格
  - **复用**: 直接调用 `UserRepo.findById()`（已有）
```

## 分析自检

写 plan 和 tasks 之前，确认：

- [ ] 是否找到了和新功能最相关的锚点模块并通读了代码？
- [ ] 是否追踪了完整的调用链（controller → service → repository → entity）？
- [ ] 是否列出了可复用的已有模块/工具清单？
- [ ] 是否确认了项目每一层的惯用写法（注解、命名、错误处理、日志）？
- [ ] plan 的每个设计决策是否能追溯到具体的源码依据？
- [ ] 需要变更的已有模块是否评估了风险？
