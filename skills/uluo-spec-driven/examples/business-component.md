# business-component.md 模板

业务组件需求清单——回答"项目需要哪些业务组件"和"承载什么业务上下文"。仅列出项目实际需要的业务组件及简短业务上下文，**不写详细组件 API/数据流/组合原子组件的方式**——详细实现由 ui-component-creator 在编码阶段产出。

> 产出路径：`specs/components/business.md`（单文件清单）

## 业务组件清单

| 组件名 | 业务上下文 | 特殊要求 |
|--------|----------|---------|
| UserCard | 用户列表/详情页展示用户基本信息（头像、昵称、标签） | 需支持批量选中操作 |
| OrderStatusBadge | 订单各状态下的可视化标签（待支付/已发货/已完成等） | 无 |
| ProductPicker | 商品选择器，用于下单/编辑购物车场景 | 需支持分类筛选 + 搜索 |
| AddressForm | 收货地址表单，用于下单/地址管理 | 需支持省市区级联 + 自动定位 |

## 填写指南

### 清单定位
- 本清单是"需求输入"，不是"实现规范"——不要越界写 API 或数据流
- 业务组件的详细实现（组合哪些原子组件、数据如何流转）由 ui-component-creator 在编码阶段基于真实代码产出
- 越界写实现细节会导致需求与实现脱节——spec 阶段写的组合方式在编码时往往已经被改了

### 组件名
- 业务组件名要能体现业务语义——`UserCard` 比 `Card1` 有意义
- 命名遵循"业务概念 + 形态"模式：`OrderStatusBadge`、`ProductPicker`、`AddressForm`

### 业务上下文列
- 说清"在什么业务场景下用"和"承载什么业务语义"
- 一句话足够——不要展开成段落
- 这是 ui-component-creator 判断实现方式的关键输入

### 特殊要求列
- 只写项目特定的额外要求——不要写"需要美观""需要响应式"这种通用要求
- 要求要具体可验证——"需支持批量选中"比"需支持更多操作"有用
- 没有特殊要求填"无"，不要留空

### 复用策略
- 业务组件的本质是"跨页面复用"——只在一个页面用的不要提取为业务组件
- 提取前先查项目已有的业务组件，避免重复造轮子

### 大小控制
- 单清单控制在 50-80 行
- 业务组件通常 5-15 个，超过 20 个说明可能把"页面片段"也当成业务组件了
