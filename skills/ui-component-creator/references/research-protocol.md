# 调研协议

组件创建 Phase 1 的方法论。定义如何系统化地建立领域知识。

---

## 两种调研模式

### 模式 A — 研究先行（Research-First）

**触发条件：** 组件所属领域不熟悉，或涉及复杂交互/专业领域（图表、编辑器、富文本、拖拽、虚拟滚动等）。

**流程：**

```
1. 知识缺口清单
   - 我对这个领域已知什么？
   - 我不知道什么？（列出来）
   - 哪些是必须知道的？哪些是 nice to know？

2. 信息源选择
   - 官方文档（最权威）→ context7 MCP
   - 业界最佳实践 → WebSearch
   - 现有实现 → GitHub 搜索 / 项目内 Grep
   - 具体技术细节 → Tavily extract

3. 检索执行
   - 一次检索一个知识缺口
   - 记录来源 URL
   - 标记矛盾信息，需交叉验证

4. 综合笔记
   - 提炼关键约束
   - 记录设计选项和 tradeoff
   - 标注仍存疑的部分
```

### 模式 B — 分析先行后补缺（Analyze-First）

**触发条件：** 组件领域有一定基础，但存在不确定点。

**流程：**

```
1. 基于现有知识完成 Phase 2 初步 API 设计
   - 正常走 Phase 2 流程
   - 对存疑部分标注 ⚠️ 待验证

2. 提取验证清单
   - 列出所有 ⚠️ 标记
   - 转为具体问题（"Vue 3 中 defineModel 是否支持多 v-model？"）

3. 针对性检索
   - 每个问题独立检索
   - 找到答案后立即回填设计

4. 修正设计
   - 更新 component-spec
   - 记录修正原因
```

## 信息源矩阵

| 信息需求 | 推荐工具 | 适用场景 |
|---------|---------|---------|
| 框架官方 API | context7 MCP | 查 Vue/React/WC 的准确 API 签名 |
| 业界最佳实践 | WebSearch | 查"how to design X component" |
| 现有开源实现 | WebSearch + WebFetch | 查 GitHub 上类似组件的实现 |
| 技术深度文章 | Tavily extract | 从特定 URL 提取内容 |
| 项目内已有实现 | Grep / Glob / SearchCodebase | 搜索项目内可复用代码 |

## 调研深度判断

| 组件复杂度 | 调研深度 | 预期产出 |
|-----------|---------|---------|
| 简单（展示型） | L1 — 快速确认 API | 确认框架 API 签名 |
| 中等（交互型） | L2 — 最佳实践调研 | 确认 API + 设计模式 + 边界情况 |
| 复杂（领域型） | L3 — 深度调研 | 确认 API + 设计模式 + 性能策略 + 可访问性 + 现有方案对比 |

**判断规则：** 涉及以下任一即为复杂——外部状态管理、大量数据渲染、复杂交互（拖拽/缩放/编辑）、专业领域（图表/地图/编辑器）。
